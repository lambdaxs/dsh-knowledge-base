# 知识库插件：功能盘点与优化路线

> 本文档基于 2026-10-30 的代码与真实 vault（112 篇笔记 / 15 个文件夹 / 47 个任务，其中已完成 38、
> 待办 13；32 张图片引用；收藏 0；标签基本未使用；仅 4 篇有手动 `orderIndex`；优先级 3 篇、截止日期 2 篇）
> 实测得出。每一条都写了「为什么」「怎么做（落点）」「验收标准」，便于直接开工。

数据结论直接决定了优先级：标签、wiki link、四态任务状态在真实数据里几乎为 0 使用，所以排在最后；
而「切换笔记丢改动」「外部改动看不到」这类问题每次使用都可能踩到，排在最前。

## 二、P0 数据安全（先做，代价小、风险最高）

### P0-1 未保存的改动会静默丢失

- **现象**：`src/client/index.js` 的 `openNote` 不检查当前是否 dirty，切换笔记直接覆盖草稿；
  关闭页面 / 刷新也没有 `beforeunload` 拦截。全部依赖用户手动 ⌘S。
- **怎么做**：两条路选一条，建议都做
  1. 切换笔记 / 切路由前判断 `dirty`，弹「保存 / 放弃 / 取消」；
  2. 停止输入 800ms 自动保存（复用 `note/save`，用 `savingRef` 串行化，避免并发覆盖 mtime）。
  另加 `beforeunload`：`if (dirty) event.preventDefault()`。
- **验收**：改一篇不保存就切走 → 有确认；改一篇后直接关标签页 → 浏览器弹提醒；开自动保存时
  输入停顿后 1 秒内落盘（列表 `updatedAt` 变化）。

### P0-2 看不到别处的改动（massCode / Spark / iCloud 同步）

- **现象**：只在 `reload()` 时扫描，工具栏手动点刷新。三端共用同一份 vault，另两端改动不可见；
  且本地有草稿时会拿旧 mtime 去写，直接撞冲突。
- **怎么做**：宿主加轻量版本号 —— `ctx.effect` 里 `fs.watch(notesRoot, { recursive: true })`
  维护 `{ revision, lastChangeAt }` 内存状态，新增 RPC `watch/state` 只返回版本号（几字节）；
  客户端每 3 秒轮询，版本变化时：无草稿 → 静默 reload；有草稿 → 只更新列表、正文保持不变并提示。
- **验收**：用 massCode 改一篇 → 3 秒内列表/详情自动更新；手改文件同样生效；
  轮询在手机端不引起明显耗电（payload < 100 字节）。

### P0-3 冲突处理只有「报错」

- **现象**：`note/save` 校验 `mtimeMs`，对不上抛错，页面只显示一行错误，用户只能刷新后重写一遍。
- **怎么做**：宿主把冲突错误带上 `code: 'conflict'` 和当前 mtime/size；新增 `note/save` 的
  `force` 与 `copy` 两个开关（`copy` 走「名字 (冲突副本).md」新建）；客户端据 code 弹三选一：
  **用我这版覆盖 / 放弃我的改动 / 另存为副本**。
- **验收**：两个页面同时编辑同一篇，后保存者看到三选一，三条路径都落到预期文件。

### P0-4 插件没有版本历史

- **现象**：代码只存在于这台机器上（宿主仓库 `.gitignore` 白名单不含 `dsh-knowledge/`）。
- **怎么做**：独立仓库 `lambdaxs/dsh-knowledge-base`（本仓库），`lib/client.js` 作为构建产物一并提交，
  保证 clone 下来能直接装机；后续每次改动先提交再重启宿主。
- **验收**：`git clone` → `pnpm add file:./` → 宿主能加载；`git log` 可回溯。

## 三、P1 列表与搜索（每天都会用）

### P1-1 列表第二行应该显示正文摘要

- **现象**：第二行是「所在文件夹」，信息量低；`description` 字段在真实数据里全为 `null`（massCode 不生成），
  不能指望它。
- **怎么做**：`scanVault` 本来就整篇读入解析 frontmatter，顺手取正文首行前 120 字生成 `excerpt`
  （去掉 markdown 标记、压空白），tree 多带一个字段，**零额外 IO**；列表第二行改成摘要，
  文件夹信息移到详情头或作为悬浮 title。
- **验收**：列表一眼能看出内容；1000 篇时 `tree` 耗时不明显上升。

### P1-2 搜索：高亮 + 打开定位

- **现象**：`search` 已返回 `snippet`，但列表没显示、没高亮；点进笔记也不会滚到命中处，
  长笔记（最长 43 KB）要靠自己找。
- **怎么做**：列表显示 snippet 并把关键词包成 `<mark>`；打开时把 query 传给编辑器，
  用 `@atomic-editor` 的 `initialRevealText`（编辑器句柄已有 `revealText`）滚动定位并高亮。
- **验收**：搜「私有化」→ 列表高亮；点进去正文停在第一处命中。

### P1-3 搜索加索引缓存

- **现象**：每次查询都全库重新读盘 + `indexOf`，112 篇约 260 KB 现在够快，但笔记数量上去会线性变慢。
- **怎么做**：宿主进程内 `Map<relPath, { mtimeMs, size, body }>`，`searchNotes` 命中 stat 就复用；
  配合 P0-2 的 watch 事件做失效，或超过 N 条（建议 2000）时限制只扫最近改的。
- **验收**：1000 篇量级下，连续搜索第二次的耗时 < 50ms。

### P1-4 最近打开

- **怎么做**：客户端 `localStorage` 记最近 20 条 path，树顶部加「最近」伪节点；
  与「全部笔记」「回收站」同一层，不需要宿主改动。
- **验收**：关页面再打开仍能看到最近列表。

### P1-5 多选批量操作

- **现象**：只能一篇一篇移动/删；45 篇的工作待办文件夹批量整理很麻烦。
- **怎么做**：列表加多选态（⌘/Ctrl 点击、移动端长按进入），底部浮动条给「移动到… / 删除」；
  宿主接口不用改，前端按序调用并在结束后统一 `reload()`。
- **验收**：一次移动 10 篇，失败项单独提示。

## 四、P2 组织与任务

### P2-1 收藏（isFavorites 字段现成）

- **怎么做**：详情头加星标按钮 → 新 RPC `note/favorite`（写 `isFavorites: 0|1`，走既有的逐字节保留序列化）；
  树顶部「收藏」伪节点，列表里可取消。
- **说明**：真实数据现在 0 收藏，但字段是 massCode/Spark 共用的，做了不会有兼容问题。

### P2-2 文件夹排序与拖拽移动

- **现象**：`scanVault` 已经把文件夹 `orderIndex` 读出来了，前端却按名字 `localeCompare` 排；
  文件夹移动只能走菜单，不能拖。
- **怎么做**：树排序改成 `orderIndex` 优先、同名兜底；文件夹菜单加载「上移 / 下移」，
  写 `.meta.yaml` 的 `orderIndex`（与 massCode 语义一致）；补 HTML5 拖拽到目标文件夹（复用已有 `folder/move`，
  需要拒绝拖进自己或子孙，选择器里已有同样的判断可抄）。
- **验收**：调整顺序后刷新仍在位；在 massCode 里看到的顺序一致。

### P2-3 任务：优先级 / 截止日期可编辑，逾期提示

- **现象**：只读展示；`priority`、`due` 字段已在数据里（3 篇 high、2 篇有截止），改不了。
- **怎么做**：新 RPC `note/task`（`priority` / `due` / `status` 三项，`undefined` 表示删键，
  `serializeNote` 已支持删键）；详情头换成下拉 + 日期输入；列表对逾期未完成的任务显示红色日期。
- **不做**：四态状态切换（真实数据只有 `todo` / `done`），以及「今天 / 即将到期」筛选 tab
  （用户上一轮明确去掉，改成逾期高亮即可）。

### P2-4 任务计时

- **现状**：Swift 版有（`TaskTimerStore`），DSH 里没有。价值取决于用户是否真的计时，**待定**。

## 五、P3 正文与附件

| 项 | 做法 | 优先级 |
|---|---|---|
| 图片灯箱 | 点击正文图片全屏预览（Esc 关闭、支持缩放），纯前端，blob URL 已有 | 高 |
| 附件管理 / 孤儿清理 | 宿主 `asset/orphans` 扫 `notes/assets` 与全库引用差集，列出后批量删除 | 中 |
| 超过 8 MB 的图 | 现在直接不显示；方案 A 提高上限（注意 base64 体积），方案 B 前端 canvas 压成 webp 再写入 | 中 |
| 大纲 + 字数 | 解析标题生成 TOC 侧栏，点击滚动；字数/阅读时间显示在详情头 | 中 |
| 在 Finder 显示 / 复制路径 | 宿主 `note/reveal`（`open -R`）+ 前端复制 `notes/<path>` | 低 |
| 导出 | markdown 直接 Blob 下载；PDF 走浏览器打印样式 | 低 |
| wiki link `[[笔记]]` | 编辑器支持、回调没接；真实数据 0 处使用，**暂缓** | 低 |
| 回收站自动清理 | 宿主在 `trash/list` 时顺带删除超过 30 天的条目（可配置），先做提示再考虑自动删 | 中 |

## 六、P4 移动端

- **现象**：≤600px 隐藏文件夹树后，**不能新建文件夹、不能换图标、不能移动文件夹**；行操作只有 ⋯ 按钮，没有长按菜单。
- **怎么做**：树改成左滑抽屉（汉堡按钮呼出），复用桌面同一套树组件；列表加长按 500ms 出菜单
  （复用现有 `openMenu`，注意滚动时取消）。
- **验收**：手机上能建文件夹、换图标、把笔记移动到任意文件夹；长按不误触发滚动。

## 七、P5 与 DSH 结合（差异化，最值得投）

### P5-1 全库问答

- **现状**：只有单篇「问 DSH」（`openChat` 拼标题 + 路径 + 正文 + 待补提问）。
- **怎么做**：`search` 取 top 5–8 命中（每篇截 1500 字）→ `uiWorkspace.startSession` 拼成
  「参考文献 1..N」草稿，末尾留提问位置；超过上下文预算时按 score 截断并注明「还有 N 篇未纳入」。
- **验收**：问「我们私有化迭代现在卡在哪」能带上多篇材料开新会话。

### P5-2 选中片段问 DSH

- **怎么做**：编辑器 `getSelection` → 详情头出现「问这段」按钮 → 草稿只带选中文本 + 出处。
- **验收**：选 3 行 → 新会话草稿只有这 3 行和路径。

### P5-3 回答沉淀成笔记

- **怎么做**：先做最稳的版本 —— 会话里选中回答文本 → 「存为笔记」→ 调 `note/create`（可指定文件夹）
  并把选中内容作为正文；进阶版读会话消息（需要确认宿主会话 API 暴露程度，**待探索**）。

### P5-4 任务派给 Bot

- **怎么做**：任务详情加「派给 Bot」，把任务正文 + 截止日期写成 prompt 开新会话，并用
  `@Bot名` 触发对应 Bot（团队里有哪些 Bot 可从会话服务读）。

## 八、P6 工程与长期

- **测试**：现在测的是 vault 层和客户端纯函数；RPC 层（27 个 endpoint 的参数校验、冲突、回收站边界）
  没有覆盖，建议补一组直接调 `createKnowledgeHandler()` 的用例。
- **构建**：`lib/client.js` 658 KB（gzip 约 225 KB）随客户端模块加载，编辑器已懒加载；
  可选进一步拆出图标选择器（846 个 SVG 的选择面板）按需加载。
- **兼容**：三个客户端同时写只靠 mtime 守护，没有锁；如果出现「写进去的字段被另一方覆盖」，
  考虑在 frontmatter 加 `writer` 标记并在冲突时提示（先观察，不提前做）。
- **发布**：定版本号（现在 0.1.0 但已远超 MVP）、打 tag、README 里的接口表随后续 RPC 同步更新。

## 九、明确不做（附理由）

| 不做 | 理由 |
|---|---|
| 标签体系与标签筛选 | 真实 vault 里 `tags` 全部为空（只有 1 处误写），做了没人用 |
| wiki link 跳转 | 真实 vault 里 `[[...]]` 出现 0 次 |
| 四态任务状态（进行中 / 阻塞） | 真实数据只有 `todo`（13）/ `done`（38），界面勾选两态足够 |
| 今天 / 即将到期 筛选 tab | 用户上一轮明确删掉，改成逾期高亮 |
| 知识图谱 / 双向链接图 | 与当前使用方式无关，投入产出比最低 |
| massCode 的其它 space（snippets / http / drawings / math） | 不在「知识库」范围；同一 vault 下这些目录本插件完全不碰 |

## 十、建议执行顺序

1. **P0 四项**（丢改动 + 外部变更 + 冲突三选一 + 入 git）—— 一次会话可完成，立刻见效。
2. **P1-1 / P1-2**（摘要 + 搜索高亮定位）—— 手感提升最明显。
3. **P5-1 / P5-2**（全库问答 + 片段问）—— 这是这个插件区别于普通笔记应用的地方。
4. **P2-2 / P2-3**（文件夹排序 + 任务字段可编辑）—— 补齐「能改」的闭环。
5. 其余按需：灯箱、TOC、批量操作、手机抽屉、附件清理。
